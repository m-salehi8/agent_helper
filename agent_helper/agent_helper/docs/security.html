ناپذیرها#

  1. دامنه‌ی کاربر: ابزارها همیشه با request.user اجرا می‌شوند؛ هسته هرگز شناسه‌ی کاربر را از خروجی مدل نمی‌خواند و ابزار هم نباید.
  2. پیشنهاد جدا از اجرا: هیچ ابزار «اجرایی» وجود ندارد. ابزار غیر فقط‌خواندنی باید proposes داشته باشد و فقط PendingAction بسازد.
  3. اجرا فقط با دکمه: confirm با قفل select_for_update، بررسی مالکیت، وضعیت، مهلت؛ idempotent؛ داخل savepoint؛ با ممیزی.
  4. مسیر سریع محافظه‌کار: فقط با اطمینان ≥ آستانه؛ خطای مدل سبک یا LLM هرگز پاسخ غلط قطعی نمی‌سازد.
  5. بدون اینترنت پیش‌فرض: همه‌ی نشانی‌ها از تنظیمات.

تهدیدها و دفاع#

تهدیددفاع
کاربر داده‌ی کاربر دیگری را بخواهد («سفارش‌های آقای X»)ابزار فقط داده‌ی user را برمی‌گرداند؛ مدل ابزاری برای کاربر دیگر ندارد
تزریق دستور در پیام یا داده («دستورهای قبلی را فراموش کن»)قاعده‌ی rule.injection؛ و حتی اگر مدل فریب بخورد ابزار اجرایی ندارد
مدل ادعا کند کاری انجام شدقاعده‌های پرامپت + اجرای واقعی فقط در endpoint دکمه
تایید اقدام کاربر دیگربررسی مالکیت ⇐ ۴۰۳
تایید دوباره / هم‌زمانقفل ردیف + idempotent
تغییر داده بین پیشنهاد و تاییدexecute دوباره بررسی می‌کند (مثلاً مبلغ)

چک‌لیست بازبینی افزونه#

  • هر کوئری ابزار با user فیلتر شده است؟
  • هیچ save()/create()/delete() در handler ابزار نیست؟
  • execute payload را دوباره اعتبارسنجی می‌کند و به params فقط به‌عنوان انتخاب از همان payload اعتماد می‌کند؟
  • برای هر مورد اجراشده actions.audit نوشته می‌شود؟
  • تست «کاربر دیگر ⇐ ۴۰۳» و «پیشنهاد چیزی ذخیره نمی‌کند» دارید؟
لاگ و حریم خصوصی

متن پیام (کوتاه‌شده تا ۱۰۰۰ نویسه) و آرگومان ابزارها لاگ می‌شوند. اگر داده‌ی حساس دارید، دسترسی ادمین به لاگ‌ها را محدود کنید و برای پاک‌سازی دوره‌ای برنامه بگذارید.
