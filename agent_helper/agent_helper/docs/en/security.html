Security model

Invariants, threats and the plugin review checklist

Invariants#

  1. User scope: tools always run with request.user; the core never reads a user id from model output and tools must not either.
  2. Proposal separate from execution: there is no "executing" tool. A non-read-only tool must have proposes and may only create a PendingAction.
  3. Execution only by button: confirm with a select_for_update lock, ownership, status and expiry checks; idempotent; inside a savepoint; audited.
  4. Conservative fast path: only with confidence ≥ threshold; a light-model or LLM error never produces a confident wrong answer.
  5. No internet defaults: every address comes from settings.

Threats and defences#

ThreatDefence
A user asks for another user's data ("Mr X's orders")Tools only return user's data; the model has no tool for another user
Prompt injection in the message or data ("forget previous instructions")The rule.injection rule; even if the model is fooled, there is no executing tool
The model claims something was donePrompt rules + real execution only in the button endpoint
Confirming another user's actionOwnership check ⇒ 403
Repeated / concurrent confirmRow lock + idempotency
Data changed between proposal and confirmexecute re-checks (e.g. the amount)
Stale proposalExpiry (10 minutes by default) ⇒ expired
Volume abusePer-minute and daily limits per user
Malicious fileOnly png/jpg/webp images, with a size limit

Plugin review checklist#

  • Is every tool query filtered by user?
  • Is there no save()/create()/delete() in tool handlers?
  • Does execute re-validate the payload and trust params only as a selection from that payload?
  • Is actions.audit written for every executed item?
  • Do you have tests for "other user ⇒ 403" and "a proposal saves nothing"?
Logs and privacy

Message text (truncated to 1000 characters) and tool arguments are logged. If you handle sensitive data, restrict admin access to the logs and plan periodic cleanup.
